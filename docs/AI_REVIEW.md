## 2. Как устроен поток (для контекста)

```
POST /ai/analyze ─ consent ─ entitlement ─ cache? ─ inflight-dedupe ─ quota ─ bg-task
   bg-task (_run_analysis, под семафором 1/воркер):
     _stage_search   3 поиска Kufar (strict / broad / без категории) + market-датасет
     _stage_extract  цена, параметры, рыночная статистика, 5 аналогов   (to_thread)
     _stage_scoring  аномалии, deal score
     _stage_photo    quick_condition (выключено по умолчанию)
     _stage_ai       Call A (цена/рынок, max 3200) ‖ Call B (состояние/риски, max 4000)
     _stage_response гардрейлы, дедуп, risk floor, кэш, task=done
```

Сильные стороны, которые стоит сохранить: двойная защита от prompt-injection (sanitizer +
HMAC-fence `ai_sanitize.py:331`), scrub ссылок/контактов в ответах модели, risk floor и
рыночные гардрейлы поверх ответа модели, частичный ответ помечается `source="partial"`,
возврат квоты при неудаче, singleflight по задаче, circuit breaker с корректным half-open.
Логика аккуратная; основные проблемы — в эффективности и в мёртвых ветках.

## 3. Находки

### 🔴 3.1. Кэш анализа фактически не работает

`api/services/ai_analysis_pipeline.py:1111`

```python
ttl = int(MARKET_ESTIMATE_TTL - (_time.monotonic() - c.started_at))
if ttl > 0:
    await c.cache.set_json(_analysis_cache_key(c.payload), serialized, ttl=ttl)
```

`MARKET_ESTIMATE_TTL = 60` (`api/services/watchlist_market.py:53`) — это TTL рыночной
оценки, а не AI-результата. Анализ идёт 30–90 с, значит TTL ≤ 30 с или запись вообще
пропускается. Проверка кэша в роутере (`api/routers/ai_analysis.py:146`) почти всегда
промахивается. Тот же паттерн в листинг-ассистенте (`api/routers/ai_listing_assistant.py:698`).

При этом в настройках лежат неиспользуемые `ai_cache_hours = 1` и
`ai_fallback_cache_ttl = 1800` (`api/config.py:213`, `:223`) — похоже, отдельный TTL для AI
когда-то был и потерялся.

**Сценарий:** два пользователя (или один повторно) открывают анализ одного объявления с
разницей в 2 минуты → 2 полных платных анализа и 2 списанные квоты вместо одной.

**Что сделать:** отдельный `AI_ANALYSIS_CACHE_TTL` (например 30–60 мин, взять из
`ai_cache_hours`); рыночные цифры в ответе уже снабжены временем выборки. Дополнительно
нормализовать `query` в ключе (`casefold` + схлопнуть пробелы, `ai_analysis_pipeline.py:101`) —
сейчас «iPhone 13» и «iphone 13 » дают разные ключи.

### 🔴 3.2. Семафор на один анализ + watchdog, считающий очередь

`ai_analysis_pipeline.py:408` — `_ANALYSIS_RUN_LIMIT = 1`, и семафор охватывает **весь**
пайплайн (`:1178`), включая поиски Kufar и сборку ответа, а не только вызов модели.
`_BG_TASK_LIMIT = 16` задач на воркер допускаются в очередь. Watchdog
`_BG_TASK_TIMEOUT = 240` (`ai_task_store.py:55`) оборачивает корутину целиком, то есть
время ожидания семафора тоже идёт в зачёт.

**Сценарий:** на одном воркере в очереди 4 анализа по ~60–70 с → четвёртый ждёт ~200 с,
стартует и через 40 с убивается watchdog'ом → «Анализ прерван». С 4 воркерами uvicorn
пропускная способность всей системы — ~4 одновременных анализа, причём распределение по
воркерам случайное.

Плюс второй ограничитель: глобальный `_chat_lock` с интервалом 1.5 с
(`ai_service.py:663`) сериализует старт **каждого** вызова модели в процессе.

**Что сделать:** держать семафор только вокруг `_stage_photo` + `_stage_ai`, поднять лимит
до 3–4 (GPT-6 Luna / Gemini paid tier легко держат параллельные запросы), а watchdog
запускать после захвата семафора (или давать ему `queue_time + 240`). Интервал 1.5 с
сделать 0 по умолчанию для OpenAI — у него свои rate-limit заголовки, а ретраи по 429 с
`Retry-After` уже есть.

### 🟠 3.3. Call A полностью выбрасывается, если нет рыночной медианы

Когда `c.median is None` (`ai_analysis_pipeline.py:1052–1093`): `fair_price → None`,
`resale_potential → None`, `negotiation_tips → []`, `market_context → NO_COMPARABLE_PRICES`,
а `similar = []`, так что и `best_pick` не используется. Из ответа Call A не остаётся
ничего — но вызов делается всегда (`ai_service.py:885–913`).

**Что сделать:** если `market_median is None`, запускать только Call B. Экономия ≈ 40 %
токенов на каждом анализе «без рынка» (редкие товары, услуги, малые выборки).

### 🟠 3.4. Мёртвый запасной путь сбора рынка

`ai_analysis_pipeline.py:665` ставит `c.market_ads = []` до проверки категории, а
`_stage_extract` (`:727–729`) переключается на датасеты когорт только при `market_ads is None`.
Пустой список — не `None`, поэтому, если `load_market_dataset` вернул `None` (сбой
запроса к Kufar), рынок строится из пустого списка, хотя три поиска уже загрузили данные.
Итог — «Недостаточно сопоставимых объявлений» и в довесок пункт 3.3. (Для объявления без
категории `build_market_comparables` и так возвращает пустой рынок — это не баг.)

**Что сделать:** инициализировать `c.market_ads = None`. Нужен тест на сбой рыночной выборки.

### 🟠 3.5. Модель пишет поля, которые потом всегда перезаписываются

Output-токены у GPT-6 Luna в 5 раз дороже input, и в анализе они дают ~65 % стоимости.
Сейчас часть вывода гарантированно выбрасывается:

| Поле | Где выбрасывается | Почему |
|------|-------------------|--------|
| `best_pick` (анализ) | `ai_analysis_pipeline.py:986` | Промпт требует `ad_id=null` (`ai_prompts.py:65`) → бэкенд всегда выбирает сам, и его `reason` не пустой → причина от модели всегда заменяется |
| `market_summary` (листинг) | `ai_listing_assistant.py:661–669` | Всегда заменяется серверным текстом |
| `pricing`, `negotiation_playbook` (листинг) | `ai_listing_assistant.py:646–649`, `:684–686` | Отбрасываются при `market.reliable == False`, но модель их всё равно генерирует |
| `competitors[].title/price_byn` (листинг) | `ai_listing_assistant.py:147–202` | Модель копирует названия и цены из контекста, а бэкенд затем нечётко сопоставляет их обратно с датасетом |
| `market_context` (анализ) | `ai_marketplace.py:485` | Используется, только если ≥ 90 символов и есть цифра — иначе серверный |

**Что сделать:** убрать `best_pick` из схемы Call A; убрать `market_summary` из схемы
листинга; при `market.reliable == False` слать урезанную схему без `pricing`/`playbook`;
конкурентов отдавать модели с индексами `[1..6]` и просить только `{"i": 2, "advantage": "..."}` —
это убирает и токены, и хрупкий fuzzy-match. Оценка: −150…−400 output-токенов на запрос.

### 🟠 3.6. Запрос к провайдеру не готов к GPT-6 Luna

`ai_service.py:633–653`: тело всегда содержит `max_tokens` и `temperature: 0.2`, а
`reasoning_effort` и `response_format` добавляются **только для Gemini**
(`_is_gemini_model`). Для `gpt-6-luna`:

* `max_tokens` — reasoning-модели OpenAI в Chat Completions обычно требуют
  `max_completion_tokens`; на странице модели это не указано — проверить до переключения.
* `temperature` — reasoning-модели OpenAI исторически принимают только значение по умолчанию.
  Тоже проверить.
* `reasoning_effort` не передаётся → у Luna по умолчанию `medium` (подтверждено в доках) —
  платим за рассуждения даже в простых `/negotiate` и `/price-advice`.
* JSON-режим не включается → парсинг держится на эвристиках `_parse_json` /
  `_repair_truncated_json`. Luna поддерживает structured outputs — `json_schema` со
  `strict: true` снимает целый класс ошибок.

Важно: 4xx (кроме 429/402) не размыкает circuit breaker (`ai_service.py:595–601`), так что
при несовместимом параметре сервис не «упадёт» заметно — каждый анализ будет молча уходить
в fallback «AI не ответил». Перед переключением нужен smoke-тест на реальном ключе.

**Что сделать:** вынести сборку тела в функцию с профилем провайдера
(`gemini` / `openai` / `generic`): `max_completion_tokens`, без `temperature`,
`reasoning_effort` по операции (`low` для tools/quick_condition, `low|medium` для анализа),
`response_format={"type":"json_schema", ...}` из уже существующих схем.

### 🟡 3.7. Фото уходят в оба под-вызова

`ai_service.py:841–847` — один и тот же `call_content` (текст + до 3 картинок) идёт и в
Call A, и в Call B. Фото нужны Call B (состояние, сток, водяные знаки). В Call A они лишь
слегка корректируют цену, и это уже отражено в `condition`. При ~765 токенах на фото
768 px — это ~2 300 input-токенов на анализ впустую (≈ 9 % стоимости на Luna, больше
на провайдерах с дорогими картинками) и лишняя латентность.

Связанное: при двойном 429 весь анализ повторяется текстом (`:919–928`), хотя каждый
`_chat` уже сделал 3 попытки — в худшем случае это 12 HTTP-запросов на один анализ.

### 🟡 3.8. Бесполезный вызов в `/ai/price-advice`

`api/routers/ai_tools.py:398–433`: если статистика рынка непригодна
(`_price_advice_stats_usable == False`), `_ground_price_advice` (`:134`) в любом случае
переписывает ответ в `neutral`. Модель при этом вызывается, а пользователь теряет единицу
квоты. **Что сделать:** при непригодной статистике отдавать детерминированный `neutral` без
модели и без списания квоты.

### 🟡 3.9. Учёт стоимости

`api/services/ai_costs.py:23–32` — нет `gpt-6-luna`, неизвестные модели считаются как $0.
`extract_ai_usage` не читает `prompt_tokens_details.cached_tokens`, поэтому кэшированный
input будет считаться по полной цене. Нужно добавить
`"gpt-6-luna": AIModelPricing(0.10, 0.50)` и поле cached-input (Luna: $0.01 за 1 млн токенов).

### 🟡 3.10. Квота не отражает стоимость

Все эндпоинты списывают одну единицу из общего окна 5 ч/7 дн (`ai_guards.py:95`), хотя
полный анализ стоит в ~9 раз дороже `/negotiate`. Это продуктовое решение, но если лимиты
задуманы как защита бюджета, стоит взвешивать: анализ = 3, листинг = 2, tools = 1.

### 🟡 3.11. Синхронный листинг-ассистент до 120 с

`ai_listing_assistant.py:609` — HTTP-запрос держится до `ai_listing_assistant_timeout = 120`
с. Если трафик идёт через Cloudflare (`cloudflared` в compose), у прокси лимит ~100 с → 524 у
клиента, при этом токены уже оплачены, а квота не возвращается (исключения на клиенте
сервер не видит). Лучше перевести на тот же task/poll-механизм, что у `/analyze`, или
опустить таймаут ниже 90 с.

### ⚪ 3.12. Мелочи

* `user_goal` принимается в `AIAnalysisRequest` (`api/schemas.py:888`), но пайплайн всегда
  передаёт `user_goal=None` (`ai_analysis_pipeline.py:922`), фронтенд его не шлёт —
  мёртвая ветка вместе с `buyer_intent_text`. Либо подключить (и добавить в ключ кэша),
  либо удалить.
* Двойная загрузка статуса аккаунта: `_check_ai_entitlement` и `_check_rate_limit` каждый
  открывают сессию БД и читают статус (`ai_guards.py:149`, `:116`) — 2 лишних запроса на
  каждый промах кэша. Можно вернуть лимиты из entitlement и передать дальше.
* Неиспользуемые настройки: `ai_cache_hours`, `ai_hourly_limit`, `ai_daily_limit`,
  `ai_quick_condition_timeout`, `ai_fallback_cache_ttl` (`api/config.py:213–223`).
* `_parse_json`, стратегия 3 (`ai_service.py:1586`): нежадный `\{.*?\}` захватывает от
  первой `{` до первой `}` — на вложенном JSON это всегда невалидный кусок; стратегия
  бесполезна (стратегия 2 уже покрывает сбалансированные объекты). Удалить.
* `collect_similar_listings_from_cohorts`: `max_pool_size` ни на что не влияет —
  `candidates[: min(max_pool_size, max_results)]` (`ai_marketplace.py:2009`).
* `consume_ai_quota`: если хранилище вернуло `allowed=False`, но ни одно окно не заполнено
  (гонка/рассинхрон), `max(blocked)` упадёт на пустом списке → 500 (`ai_quota.py:83`).
* При включённом photo precheck одни и те же 3 фото скачиваются и сжимаются дважды
  (`_stage_photo` и `_stage_ai`) — стоит переиспользовать base64.
* При срабатывании `wait_for` (150 с) HTTP-запрос к модели отменяется, но генерация у
  провайдера уже оплачена — ещё один довод держать `max_completion_tokens` поменьше.

### 4.4. Куда давит стоимость и что даст оптимизация

Output + reasoning ≈ 65 % стоимости анализа, поэтому самые выгодные рычаги — про вывод:

| Мера | Экономия на анализе |
|---|---|
| `reasoning_effort: low` для Call A и tools (Call B оставить `medium`) | −15…25 % |
| Убрать выбрасываемые поля (3.5) | −5…10 % |
| Фото только в Call B (3.7) | −9 % |
| Не вызывать Call A без медианы (3.3) | −40 % на таких объявлениях |
| Рабочий кэш (3.1) | весь повтор бесплатно |
| Prompt caching статичной части system (~1–1.5K ток.) | ≤ 5 %, запись стоит 1.25×; низкий приоритет |

С первыми тремя мерами анализ ≈ **$0.0017–0.0019**. Batch/Flex (−50 %) для интерактивных
запросов не подходит — только если появятся фоновые AI-задачи в scheduler.

### 4.5. Чек-лист переключения на GPT-6 Luna

1. Профиль OpenAI в `_chat` (3.6): `max_completion_tokens`, без `temperature`, явный
   `reasoning_effort`, `json_schema` из существующих схем.
2. `AI_BASE_URL=https://api.openai.com/v1`, `AI_MODEL=gpt-6-luna`;
   `_default_listing_assistant_model` сейчас подставляет облегчённую модель только для
   Gemini — решить, нужна ли такая подстановка.
3. Цена в `ai_costs.py` + учёт `cached_tokens` (3.9).
4. Проверить картинки: data URL JPEG 768 px подходит; можно явно задать `detail: "low"` для
   Call A, если фото там останутся.
5. Обновить `ai_provider_name` / `ai_provider_region` и текст согласия на трансграничную
   передачу (провайдер меняется с Google на OpenAI).
6. Smoke-тест на реальном ключе: по одному вызову каждого `operation` и проверка, что
   `source == "ai"`, а не `fallback`.
